# Studio EFS mount helper provisioning

Every new CPU/GPU stack owns an `EfsClientAssociation` in AWS Systems Manager State Manager. Its command document invokes the Debian EFS build functions from the already-downloaded RES 2026.06 installer independently of the local CLI. The association targets the unique `StudioStackId` launch tag, including a node that registers with SSM after stack creation. Its stack-owned dispatch role permits only `ssm:SendCommand` for that instance and command document. CloudFormation creation acknowledges the template's IAM resources and does not wait for helper installation.

Package selection follows RES commit `1f526a241fb293a29fb018f08ccf81c100c05a42`: the native functions read `package_config.yml`, clone the current `aws/efs-utils` source, use Rust's stable toolchain, build the Debian package and install it. There is no standalone EFS version pin or Distributor package. The caller sources `scripts/common/linux/debian/nfs_utils.sh` and invokes its functions directly so upstream's watchdog-only presence check cannot skip a broken mount helper. Native source, configuration and build-function bytes remain unchanged.

The document first requires the RES-ready marker, then runs `mount.efs --version`. A working helper ends the attempt successfully before any build or package operation. A missing or broken helper triggers the native build in a fresh temporary directory, with a 20-minute command timeout and cleanup on shell exit. The caller restores PATH after the native RETURN trap. If installation returns without a working helper, APT reinstalls only the package just built; a final version check must succeed. This handles an installed package whose files are missing without choosing another source or version. A failed build, install or verification fails the attempt. RES's unchanged Rust helper manages Rust under root's home and calls `rustup self uninstall`; the temporary build directory does not isolate a pre-existing root Rust toolchain.

For newly created timed desktops, the existing readiness Automation invokes this same document before checking complete workstation readiness. A missing RES-ready marker ends the attempt immediately; the native workflow retries after 60 seconds and rechecks instance/SSM availability. Once RES is ready and SSM can deliver commands, installation starts on the next retry, normally about one minute plus API/delivery time, instead of waiting for the next 30-minute association run. The existing 60-minute setup deadline and 20-minute build timeout remain in force. There is no long-lived prerequisite-wait command spanning a RES reboot.

State Manager still applies the association initially and every 30 minutes as a fallback. Both callers use one nonblocking `flock` around the installer and recheck the helper after acquiring it, so overlapping attempts cannot build concurrently. A busy lock fails that attempt for a later native retry. The existing guest service resumes across reboots. Shared document controls require SSM Agent 3.0.502 or newer. No local CLI continuation, new daemon, AWS resource or custom retry loop is added.

The existing guest setup completes asynchronously; `--no-studio-software` skips Rez and the Ollama startup service, while shared storage remains required. The optional immutable Rez 3.4.0 bundle contains no EFS `.deb`. Updating the CLI does not alter existing stacks or upgrade a working helper. Stack destruction removes the association, document and dispatch role through CloudFormation.

The guest `studio-software-setup.service` waits for DCV readiness and requires `mount.efs`. If the helper is absent, it retries after 30 seconds without blocking DCV. It mounts `fs-054fd0b72429f4569` read/write using `tls,iam`, then exposes `/opt/studio/packages/shared` at `/studio`. New desktop accounts and the shared directory use UID/GID 2000. Only after storage succeeds does optional, checksum-verified Rez installation begin.

The script migrates the exact previous read-only fstab entry, accepts its own existing `/studio` link, and reports unrelated conflicts. It creates only the new shared directory; it does not recursively change old package ownership. The publisher also exposes `/studio`, but ordinary desktop writes do not require a publisher or Rez.

`StudioWorkstationSSMRole` uses inline policy `StudioEfsSharedWrite`, recorded in `infra/workstation-efs-write-policy.json`, for mount/write access to this filesystem over TLS through its mount targets. It replaces `StudioEfsConsumerMountRead`. The existing default EFS filesystem policy remains in place; this change does not deploy the historical review-only resource policy or claim a new filesystem-wide access boundary.

A clean setup requires SSM connectivity and network access to Ubuntu package repositories, GitHub, Rust's distribution service and Cargo's dependency sources. Inspect the readiness Automation's `installEfs` step and its Run Command output, the fallback `EfsClientAssociation` history, and `journalctl -u studio-software-setup.service` for failures. Helper build failures do not block DCV; existing automatic-stop safeguards still apply.

**Current validation:** generated-shell tests cover arbitrary selected package versions, healthy-helper preservation, native build failures, partial-package reinstall, final verification, fresh retry workspaces, lock contention and the helper becoming healthy between concurrent attempts. Workflow checks cover prerequisite ordering, exact document/instance authorization and the bounded native retry cadence. Fresh CPU/GPU acceptance of the prompt trigger remains outstanding, including client disconnection, writable `/studio`, preservation of shared data and reboot continuation. Earlier acceptance below does not establish acceptance of this change.
