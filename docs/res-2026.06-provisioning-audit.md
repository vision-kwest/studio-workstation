# RES 2026.06 Ubuntu workstation provisioning audit

> **Historical original RES source audit:** Earlier unknowns about the runtime bootstrap, reboots and GPU/DCV dependencies were investigated before the merged standalone implementation. This source trace is preserved as research evidence. For tested final runtime behavior, S3 pins and command-line deployment see [runtime provenance](../runtime/README.md) and [Studio CLI](studio-cli.md).

**Status:** source-grounded investigation, not a tested standalone implementation. Source tag: [aws/res 2026.06](https://github.com/aws/res/tree/2026.06). Scope: Ubuntu 24.04 x86_64, CPU and NVIDIA DCV console sessions.

## Verified shell call graph

```text
virtual-desktop-host/linux/install.sh
  -> common/linux/bootstrap_common.sh + config_common.sh
  -> common/linux/install_common.sh
       -> AWS SSM (conditionally), jq/yq, system_packages, CloudWatch, Python, etc.
  -> common/linux/disable_nouveau_drivers.sh (GPU only)
  -> common/linux/kernel_hold.sh (conditional)
  -> dcv/linux/debian/dcv_server.sh: install_prerequisites()
       -> apt install packages from package_config.dcv.host.prerequisites.debian.ubuntu
          (ubuntu-desktop, gdm3)
  -> first reboot (when PREBAKING_AMI=false)
  -> virtual-desktop-host/linux/install_post_reboot.sh
       -> dcv/linux/dcv_server.sh
            -> dcv/linux/debian/dcv_server.sh (source)
            -> dcv/linux/gpu_drivers.sh (GPU only)
            -> install_nice_dcv_server()
            -> install_microphone_redirect()
            -> install_usb_support()
            -> install_modified_x_server() (dummy Xorg only on CPU)
       -> install SSM agent at end
       -> second reboot (when PREBAKING_AMI=false)
       -> common/linux/install_app.sh (virtual-desktop-app)
            -> Python RES agent and session/bootstrap configuration
```

**Critical distinction:** `install.sh` and `install_post_reboot.sh` default `PREBAKING_AMI=true`, and explicitly avoid self-initiated reboots in Image Builder. Therefore, the above runtime reboot sequence cannot be copied verbatim into Image Builder. We need to map AWSTOE restart handling and validation separately.

## Differences versus PR #3

| Concern | RES 2026.06 | Our draft v0.3 |
|---|---|---|
| Desktop dependencies | `ubuntu-desktop` and `gdm3`, sourced from config | `ubuntu-desktop-minimal`, GDM, Xorg, dummy driver in one apt command |
| Installation staging | Common dependencies, desktop, reboot boundary, DCV/GPU, reboot boundary, RES app | Desktop and DCV in separate Image Builder components, without matching RES staging |
| Headless Xorg | Writes `/etc/X11/xorg.conf` with dummy device, `Virtual 4096 2160`, and `VideoRam 512000` | Writes `/etc/X11/xorg.conf.d/20-studio-dummy.conf` with custom 1920x1080 modeline |
| DCV packages | Server, web viewer, `nice-xdcv`, and GPU-only GL package | Server and web viewer only |
| GPU drivers | Instance-family-specific NVIDIA GRID/public selection, `nvidia-xconfig` | Not implemented |
| DCV authentication | RES external auth verifier + broker/ALB endpoint | Local `authentication="system"` (intentional standalone change) |
| Session startup | RES Python agent sets console owner/permissions and starts services | Simplified `dcv.conf` and smoke test |
| Readiness | Xorg access check and retries; DCV service and `dcv list-sessions` | `pgrep Xorg`, `dcv list-sessions`, port check |
| GNOME | Startup animation workaround in Python | Not implemented |

**Implication:** PR #3 is not a minimal infrastructure-only extraction of RES; it materially rewrites the desktop stack. Reconcile these differences before another paid build.

## RES dependencies to remove/replace

- Remove RES identity/directory/SSSD and project storage assumptions, not ordinary Ubuntu login.
- Replace RES `auth-token-verifier` endpoint and connection gateway with DCV system authentication and restricted direct HTTPS on 8443.
- Replace RES session owner/id, broker token, internal ALB URL, and project EFS mount with one local `workstation` user and local persistent EBS.
- Replace RES agent lifecycle, idle detection and permissions file with standalone service/session readiness and a separately designed stop mechanism.
- Preserve GNOME/Xorg/DCV startup ordering and retries where needed, without carrying RES Python package dependencies wholesale.

## Unresolved items (do not guess)

1. **Exact apt hang cause:** the last log line `gdm.service is not active, cannot reload` is not proof of a GDM deadlock. The shell command might still be blocked in apt/dpkg, needrestart, systemd, debconf, or another postinst process.
2. Full Python `install_app.sh` call graph and exact timing of `gnome_utils.py`/Xorg/DCV setup remain to be traced. Do not claim the shell scripts alone create a working RES desktop.
3. AWSTOE reboot and SSM reconnection behavior in Image Builder must be tested with component boundaries.
4. DCV system-auth console login behavior and initial password provisioning must be tested on a fresh AMI; a running service alone is insufficient.
5. GPU build must use actual NVIDIA instance hardware; a CPU builder cannot validate NVIDIA acceleration.

## Recommended next engineering decision

Keep CloudFormation + Image Builder as the inexpensive managed build orchestration *if* it can accommodate the RES stage boundaries. Port verified RES package lists, dummy Xorg config, DCV packages, and service readiness in small reviewable components. Build CPU first, then GPU. Do not deploy an unreviewed patch that merely suppresses GDM errors.

## Acceptance gates

1. CloudFormation validates, Image Builder AWSTOE schema validates, and the exact recipe/image version is traceable.
2. Image Builder completes installation with bounded execution time, retains logs, reboots and reconnects.
3. Clean cloned instance passes Xorg/GDM/DCV console checks after cold boot and stop/start.
4. Human or automated browser DCV login verifies a usable GNOME desktop.
5. For GPU: `nvidia-smi`, Xorg NVIDIA renderer and GPU-accelerated DCV verified.
6. AMI contains no active user passwords, secrets, RES broker credentials or environment-specific trust tokens.
